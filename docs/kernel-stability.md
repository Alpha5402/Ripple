# K6：内核稳定化验证

K6 已接入 SQLite/FTS5，完成按中心语义检索、引用缓存、结构化错误与覆盖状态，并通过 CLI 和最小 HTTP Host 调用同一 SDK。[完整 API](kernel-api.md)说明生命周期和并发契约；这一阶段没有进入正式 App。

## 规模测量

Apple M5、16 GiB、Node.js 24.15.0。三组分别在独立 Node 进程运行，最终测量时已停止本地模型服务。数据为 1k/5k/10k 篇合成 Markdown，每篇约 370 字节、三个章节，包含一个自然提及和一个显式链接。

语义部分给每篇配置一个合成、归一化的 2048 维向量；它们故意产生密集候选以测量扫描、排序和文档去重。**没有调用模型，不代表万篇长文的编码时间或推荐效果。** SQLite 的文档、FTS 和向量确实落盘，不使用假存储。

| 操作 | 1k 文档 | 5k 文档 | 10k 文档 |
| --- | ---: | ---: | ---: |
| 导入、解析、关系和 FTS 提交 | 421 ms | 2011 ms | 3910 ms |
| 无向量重启、载入与投影构建 | 52 ms | 250 ms | 541 ms |
| 首次语义 Snapshot，P95 | 16.1 ms | 56.4 ms | 101.1 ms |
| Lens 本地过滤，P95 | 1.29 ms | 1.31 ms | 1.32 ms |
| 持有向量缓存时修改一篇正文，P95 | 20.4 ms | 90.0 ms | 241.6 ms |

首次 Snapshot 取 20 个不同中心，Lens 遍历 0～100，共 101 次；增量更新只有 5 次样本，P95 在这里就是该小样本的最大值。导入和重启为单次观测。结果是本机基准，不能当作稳定延迟上限或正式性能承诺。

10k 场景 Snapshot 约 138 KB，包含 103 条候选：语义 Top-100 加尚未包含的确定关系。文档更新后仅相关旧向量失效，剩余 9995 个有效单元，总体 coverage=partial。此增量时间包含内核状态、关系投影与 SQLite 提交，**不包含新向量编码**。

原始报告还记录了确定性 Snapshot、搜索、向量落盘/激活/重启与内存：[1k](../reports/k6/benchmark-1000.json)、[5k](../reports/k6/benchmark-5000.json)、[10k](../reports/k6/benchmark-10000.json)。10k 进程末尾 RSS 约 2.39 GiB，含向量副本、对象和尚未回收的堆；不是最小稳定占用或峰值测量。真实长文通常有多个单元，计算与内存会随单元数增长。

```sh
npm run benchmark:kernel -- --documents 1000
npm run benchmark:kernel -- --documents 5000
npm run benchmark:kernel -- --documents 10000
```

## 支撑规模的实现变化

名称匹配从“每篇遍历全库名字”改为复用字面 trie；批量导入通过 Map 查找 ID 和路径。实体目标没变化时复用未修改文档的引用投影，名称、路径、章节目标或别名变化时仍完整重新解析引用，保留正确性。

确定关系有按节点邻接索引。语义从提交时计算全库两两向量，改为访问中心时精确扫描当前有效单元；缓存的中心结果先按文档预算截断，最多保留 32 个中心。Snapshot 有效性校验使用单元哈希索引，Lens 不扫描全库向量。

FTS 删除使用 rowid，只更新真正变化的文档。新文档不再反复扫描已有 FTS 行。SQLite 根据不可变前后状态跳过未变化的向量空间；向量确实变化时按记录哈希增量写入，不让普通正文提交重复处理整库向量。

## 正确性与真实路径

当前 **73 个测试**通过，另有 typecheck 和构建。新增覆盖：

- SQLite 重启恢复身份、用户声明、评分策略与相同向量数值；旧 JSON 一次迁移；删除后重新导入不会复活旧证据。
- 两个实例写入冲突时，数据库、FTS 和内存一起回滚；未知 schema、已关闭连接返回明确错误。
- Provider 激活或向量发布提交失败时，coverage 不宣称未提交向量已经 ready；损坏的向量字节可丢弃重算。
- 中文分词搜索；`Array.from` 与 `Array.fromAsync`、完整型号与其扩展型号、大小写、短符号的不同匹配。
- 按中心语义结果与小规模穷举参考一致；原有方向、证据、快照和 Lens 性质测试继续通过。

真实 iWiki 索引 **77 篇、386 个 WeMM 单元，coverage=ready**；全库 Markdown 哈希保持一致。新 CLI 进程从 SQLite 重启并 index，得到 **encoded=0、reused=386**，完成 Event Loop 展开、证据查看、切换到 Web Workers 再返回和 SSRF 全关系查询。[可提交摘要](../reports/k6/wiki-summary.json)不包含私人原文；原始日志保留在忽略目录。

第二个 Host 通过实际回环 HTTP 完成创建会话、聚焦 CSRF、Lens 展开、证据读取、切到邻居并返回原 Snapshot，精确搜索可用。Origin 与 Host 拒绝路径也实际验证，[记录](../reports/k6/http-host.json)已保存。其 handler 还通过独立测试；Core/SDK 的依赖检查确认不引用 CLI、Node 或 UI。构建后的包导出也实际调用了 SQLite、反向关系、搜索和 ExplorationSession。

## 尚未覆盖的边界

SQLite 使用同步 Node API；千篇以上的导入和较大的更新会占用调用线程。正式桌面/网页宿主应放到自己的工作线程或进程中，并提供进度显示。此次没有实现后台 watcher、进程间自动合并、ANN 或产品级任务调度。

存储事务和冲突测试不等于断电/磁盘损坏故障注入。性能没有覆盖每篇数十单元、百万单元、长期运行或多用户并发负载。K5 的参考评分和真实人工发现记录也必须分开解读，见[关系评估](relation-eval.md)。
